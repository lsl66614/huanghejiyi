> 状态：P0–P3 已全部改代码或作出书面取舍；运行验证仍待可用构建环境

> 目标：先补“档案连续性”，再补“文物发现”，最后补“推荐与回顾”，然后进入模拟器验收，真机项单列待办

## 0. 结论先行

当前产品的内容厚度足够，问题不在“有没有内容”，而在“用户做过的事有没有地方沉淀”。

遗址线是完整的：浏览 → 详情 → 收藏/笔记/进度 → 推荐 → 网络图 → 同步。文物线和笔记线都停在半程：104 件文物没有全局入口，笔记按 target 碎片化，收藏之后缺少一个“回看自己档案”的目的地。

对标之后，最值得补的不是更多页面，而是四个“连续性”：

1. **记录连续性**：随手记 → 归到遗址/文物 → 全局找到 → 回顾；
2. **收藏连续性**：收藏 → 分类 → 最近删除 → 再次访问；
3. **发现连续性**：文物图录 → 相关文物 → 主题路线 → 推荐；
4. **同步连续性**：状态可见 → 冲突可解释 → 断网恢复自动补 → 误删可找回。

建议按 P0 → P1 → P2 分三段做，P0 只修一致性与可信度，P1 补文物与搜索，P2 再做推荐解释、路线和回顾。音频讲解、地图导航、AR/3D、社区、账号云服务继续明确不做。

## 1. 对标结论

### 1.1 文博/博物馆 App

| 产品/研究 | 可借鉴机制 | 对黄河记忆的落点 |
|---|---|---|
| Google Arts & Culture | 高清缩放看细节、策展式展览、按年代/颜色浏览、相关作品 | 文物多图与查看器；“今日一物”；相关文物 |
| 博物馆 App 研究（Curator） | 收藏/书签 + 数字档案回看；多层内容（速览/分析/故事）；主题路线 | “我的档案”；详情页“速览/深读”；主题路线 |
| Museums Association 指南 | 基于兴趣/历史行为的个性化推荐；无障碍是核心目标 | 推荐解释与冷启动兴趣选择；夜间模式列为可选 |
| Whitney 移动导览 | 首屏先帮用户定位；字幕/声音描述默认可见；夜间模式 | 首页“继续研读/今日一物”减少选择成本；错误态与空态写清楚 |

关键结论：文博产品的“收藏”不是终点，而是**参观后回看**的入口。当前 FavoritesPage 已经有分组和标签，缺的是“从收藏回到内容”的路径和“最近删除”的安全感。

### 1.2 笔记/知识管理

| 产品 | 可借鉴机制 | 对黄河记忆的落点 |
|---|---|---|
| Flomo | Inbox 低摩擦记录；多级标签；每日回顾；随机漫步；相关笔记；快捷搜索；批注 | 笔记中心（全部/随手/遗址/文物）；每日回顾；相关笔记；全局搜索 |
| Obsidian | Backlinks；Local Graph；Unlinked mentions | 遗址/文物详情的“相关笔记”；以当前条目为中心的局部网络图 |
| Notion | 数据库视图与筛选 | 笔记中心按 target 类型/标签/时间筛选 |

关键结论：笔记产品把“收件箱”当作缓冲区，不要求用户当场分类；黄河记忆现在把 `notebook:inbox` 当成一个普通 target，导致“我的”页统计全部笔记、入口却只显示随手笔记。先把这个语义改对，再谈回顾。

### 1.3 推荐/发现流

| 机制 | 行业做法 | 对黄河记忆的落点 |
|---|---|---|
| 解释 | 先给 1–2 条最强理由，可展开；“因为你看过 X” | 推荐页顶部显示种子来源；卡片默认 2 条理由 |
| 负反馈 | “不感兴趣/少看这类”，并确认生效 | 推荐卡片加“不感兴趣”，写入本地反馈表 |
| 冷启动 | 轻量兴趣选择，不用长问卷 | 首次进推荐页选 2–3 个年代/类型 |
| 多样性 | 控制同一类型/年代占比 | 12 条结果按年代/类型配额 |
| 去重 | 排除已看/已收藏/刚推荐过 | 现有已排除收藏；再排除最近浏览与上一轮推荐 |

关键结论：当前推荐是“算得出来”，但“为什么是它”只在卡片上堆理由；冷启动直接拿语料第一条做种子，用户不知道。补解释和负反馈，比换算法更划算。

### 1.4 鸿蒙多端协同

| 来源 | 可借鉴机制 | 对黄河记忆的落点 |
|---|---|---|
| 华为分布式数据库冲突处理 | 官方默认 LWW，不提供冲突回调；开发者要自己提示用户 | 冲突中心 + 同步状态条，不能静默覆盖 |
| 华为备忘录用户反馈 | 同步慢、静默覆盖会被当成丢数据；有“最近删除” | 最近删除（30 天）；同步失败可见、可重试 |
| 鸿蒙多设备协同实践 | 明确“谁在编辑/正在同步/失败重试”的状态 | 全局同步状态：空闲/同步中/已同步/失败/离线 |
| 华为云空间备忘录 | 开关同步后多端实时更新；删除进最近删除 | 模式持久化；启动/回前台补同步 |

关键结论：同步引擎已经有了，缺的是**用户能看见同步正在发生**。当前 `realMode` 不持久化、冷启动不检查网络、冲突只在同步页里看，这三处会让“自动同步”在答辩时站不住。

## 3. 目标功能清单

### P0：一致性与可信度（先做，改动小、收益大）

#### P0-1 笔记中心

**用户故事**：我写了一条遗址笔记、一条分段笔记、一条随手笔记，打开“笔记”能看到全部，并按类型筛选。

**交互**：
- 入口：底栏“笔记”与“我的 → 随手笔记”都进同一个 `NoteCenterPage`。
- 顶部筛选：全部 / 随手 / 遗址 / 文物；二级标签筛选沿用现有 tag。
- 列表按更新时间倒序，每条显示：正文摘要、所属遗址/文物、标签、时间。
- 点击进入原 `NotePage` 编辑；长按或更多菜单提供“关联到遗址/文物”“移动”。
- 搜索框支持正文与标签关键词。

**数据**：
- 不新增表；`allNotes()` 返回全部未删除笔记，补 `targetKey`、`targetType`、`targetTitle`。
- “随手”= `target_key = 'notebook:inbox'`；“遗址”= `site:` 前缀；“文物”= `relic:` 前缀。
- “关联/移动”只改 `note.target_key` + `updateTime` + `deviceId`；note_id 不变，同步仍按行收敛。

**验收**：
- “我的”页笔记数 = 笔记中心“全部”条数。
- 写 1 条遗址笔记 + 1 条随手笔记，筛选“随手”只剩 1 条。

## 5. 数据与同步影响

**不新增同步表**。现有六表（favorite / favorite_tag / note / note_tag / tag / progress）足够支撑 P0–P1。

新增的本地数据只有两类：

1. `reco_feedback`：推荐负反馈，本地表，不参与分布式同步；换设备后推荐偏好不迁移，这是可接受的。
2. `meta` 键：`syncMode`、`lastSyncResult`、`lastSyncError`、`lastSyncConflicts`、`recentSearches`；都走现有 meta 接口。

**需要谨慎的改动**：

- 笔记“关联/移动”改 `target_key`，note_id 不变；同步按 note_id 收敛，不会产生新行。改完必须同时更新 `updateTime` 与 `deviceId`，否则 LWW 会判旧。
- 最近删除依赖 `isDeleted=1` 与 `updateTime`；恢复时置 0 并更新时间。不要物理删行，否则对端会“复活”。
- 文物图录、今日一物、路线都从语料派生，不改 `sites/*.json` 的 schema；路线单独放 `routes.json`，避免污染遗址 JSON。
- `syncMode` 持久化后，启动时 AutoSync 要用同一个模式；不要在启动时默认回仿真，否则用户会以为数据丢了。
- 若后续做“设备面板”，只读 `deviceId` 与 meta，不新增同步域。

## 8. 风险与不做

**风险**：

- 文物只有 15/104 件有实拍，图录做出来后“线稿占位”会更显眼；必须用“实拍/线稿”角标和统一材质插画，不要假装全是照片。
- 三维筛选 88/120 为空；增加文物图录后，用户会更容易发现内容分布不均。空态文案要写好，不要用“暂无数据”四个字糊弄。
- 推荐负反馈是本地表，不同步；换设备后偏好丢失。要在文档里说明，不要暗示“跨端记住口味”。
- 最近删除依赖墓碑；如果用户在对端恢复、本端已超过 30 天，仍可能被同步回来。要么接受，要么加“本端已清理”标记，后者需要新列，建议先不做。
- 自动同步涉及权限与生命周期，模拟器只能验一部分；真机项必须单列，不要用仿真结果冒充。
- 新增页面会触碰设计门禁（对比度、间距、字号）；每加一页先跑 `run_gates.py`，不要最后一次性补。

**明确不做**：

音频讲解、地图导航、AR/3D、社区分享、账号体系、云端服务、AI 生成内容。理由不变：赛题不要求，工期有限，且会稀释“分布式个人档案”的主线。

另一项是本轮新加的：**夜间模式的运行时切换**。它不是“多一个开关”，而是要把全部颜色从构建期常量改成可观察状态并逐页验证对比度，见 0.1 的取舍说明；与其留一个深色下看不清的半成品，不如保持单一浅色主题。

导出只写一个文件，不提供“一键恢复/导入”：导回的语义要和同步的 LWW 合并对齐（同一条笔记哪个更新时间为准、标签是否重建），在没有构建环境验证的情况下贸然实现，风险高于收益。JSON 里已把 `targetKey`、时间戳、标签全带上，将来做导入不必改格式。
