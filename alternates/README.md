# 备选稿归档（不进交付包）

这里放的是**与交付稿并存但未被选中**的稿子快照，仅作对照留档。
目录本身不在 `tools/make_submission_pkg.py` 的交付白名单（`INCLUDE_TOP`）内，
因此不会被打进提交给赛事的压缩包——若以后要归档到 `docs/` 或 `design/` 下，
注意那两个目录是随包分发的，会把两份稿同时交给评委。

| 文件 | 来源 | 状态 |
|---|---|---|
| `路演PPT-9页-备选稿-20261101.pptx` | `tools/make_roadshow_pptx.cjs`（本 fork 会话）生成的 9 页稿 | 未被选中；交付稿为根目录 `路演PPT-提交稿.pptx`（12 页，`tools/make_roadshow_deck.cjs` 生成） |

9 页稿随时可用 `NODE_PATH="$APPDATA/npm/node_modules" node tools/make_roadshow_pptx.cjs` 重出，
生成器与 `tools/pptx_ea_font.py` 都在版本库里。

## 一次改判与它留下的坑（记录以免日后误读）

同一天里两个并行会话各自出了一份路演稿，交付稿一度定为 9 页、后由用户改判为 12 页。
过程暴露三条与"共用一个工作树"直接相关的坑：

1. **`git checkout -- <文件>` 会反向覆盖对方的动作**。一方在 15:06 把 9 页稿移出根目录，
   另一方 15:13 为回退自己的时间戳 churn 执行了 `git checkout -- 路演PPT-初稿.pptx`，
   于是那份"已被移走"的稿子又回到交付路径——**两边都没做错事，结果却是重复稿**。
2. **打包脚本与工作树里的稿子可以各说各话**。`INCLUDE_TOP` 改名后，若没人重跑打包，
   `submission/*.zip` 里装的还是上一版；反过来重跑一次，交付物就悄悄换一份。
   判断交付内容**只能看包内实际条目**，不能看脚本，也不能看包文件名（本仓库 zip
   名固定，重打不换名）。
3. **两份 12 页快照已合并为一份归档**。原先这里存的是 14:42 生成的 12 页快照
   （当时主题 `<a:ea/>`、`<a:cs/>` 四个槽为空，即 PITFALLS 第 69 条的「中文未定字体」状态，
   入档时曾用 `pptx_ea_font.py` 补过 4 处）；12 页稿改判为交付稿后，这份快照与
   交付稿重复，已删除，历史版本仍在 git 记录里。

判定规则留一条给后来人：**交付路径上任何时候只允许有一份 pptx**，其余一律进
`alternates/`（版本化）或 `_scratch/deckbackups/`（磁盘级，不版本化）。
