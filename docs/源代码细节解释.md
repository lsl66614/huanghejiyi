## 1. 分层的真相：三块而不是六层

`设计方案.md` §3.1 画了六层自上而下。实际 import 关系核验下来是这样：

**符合预期的部分**

- `model/` 是**纯叶子**：0 处外部 import，只被上层引用。
- `pages → repository / service / common / model` 单向。
- `repository → model` 单向，内部用 `IDataRepository` / `ITransport` 两个接口隔离实现。
- `service/` 下 19 个文件确实无 `@kit` import，文件头以「禁 @kit」自述。

**三处有意突破边界**
1. `service/sync/AutoSync.ets:14-23` 引 `@kit.NetworkKit` / `AbilityKit` / `PerformanceAnalysisKit` —— 网络监听与真机 transport 有副作用，不可能纯函数化。
2. `common/AppNavBar.ets:22`、`RelatedNotes.ets:14`、`SyncStatusBar.ets:7` **反向依赖 `service/`**（3 处）。
3. 于是「层次」实际是**三块**：`common(设计语言) ← pages ← service/repository` 的混合。

> **结论**：`service/` 的「纯」是**按目录逐文件**保证的，不是按层保证的。README 说「service/ 纯函数」，应读作「service/ 下 19 个文件是纯函数，`sync/` 下 2 个不是」。这是文档口径与实现口径最值得记住的一处差异。

**为什么要较这个真**：因为「纯」的判定直接决定能不能进 Node 测试体系 —— 见 §6。

## 2. 同步三步：`runSync` 是整个系统的心脏

`service/sync/SyncScheduler.ets`（48 行，全文最值得逐行读的文件）。

```ts

export async function runSync(deviceId: string, repo: IDataRepository,
  transport: ITransport, onProgress?: ProgressCallback,
  paceMs?: number): Promise<ConflictEntry[]> {
  const pace: number = paceMs === undefined ? 0 : Math.max(0, paceMs);
```


**三个设计点**：

## 3. 传输抽象：8 行接口撑起两条演示路径

`repository/ITransport.ets` 全文只有 8 行：

```ts
export interface ITransport {
  exchange(deviceId: string, local: Map<string, SyncRecord[]>): Promise<Map<string, SyncRecord[]>>;
  notifyAfterSync(deviceId: string, finalTables: Map<string, SyncRecord[]>): Promise<void>;
}
```

`exchange` 的注释写着「返回对端（或对方设备档案）的五表快照」（实际是六表），`notifyAfterSync` 写着「合并完成后回写，使下一轮对端能看到本轮终态（**收敛语义**）」。

### 3.1 仿真：`LoopbackAdapter`（65 行）

```ts
// :27-29
// profiles[X]：X 的对端（=对方身份）在上一轮同步时的档案快照。
// 只在对方 exchange 时写入（播种）或 notifyAfterSync 后收敛，从不被本机覆写。
private profiles: Map<string, Map<string, SyncRecord[]>> = new Map();
```

```ts
// :40-51
async exchange(deviceId, local) {
  // 先把本机当前档案留给对端：对端下一轮同步时，exchange 取到的就是它
  this.profiles.set(LoopbackAdapter.peerOf(deviceId), cloneTables(local));
  const theirs = this.profiles.get(deviceId);
  if (theirs === undefined) {
    // 首次同步：对端档案尚未建立，按空档案合并（本机数据全量保留）
    ...
  }
  return cloneTables(theirs);
}
```

**这里藏着一个必须理解的翻转**：`exchange` **既读又写** —— 它一边返回对端档案给本机，一边把本机档案存进去留给对端下一轮。所以一次同步实际上「交接」了两份档案。

> 早期版本把合并结果**同时写回两份袋**，导致两侧永远一致 ——「首次冲突能演示，之后同一冲突不再产生记录」。现改为 `notifyAfterSync` **只写对方一份**（:54-56）。这就是为什么「同一冲突能反复演示」。（注意：袋只活在内存，进程重启即失效 —— 台上第二次演示失效的根因在此。）

### 3.2 真机：`SoftBusRdbTransport`（71 行）

## 4. 合并引擎：60 行里的三个决策

`service/merge/MergeEngine.ets`。

### 4.1 主流程

```ts
// :12-22 用 Map 建索引，key 是逻辑身份
export function mergeElementSets(local: SyncRecord[], remote: SyncRecord[],
  table: string = ''): MergeResult {
  const localMap: Map<string, SyncRecord> = new Map();
  for (const r of local) { localMap.set(r.key, r); }
  ...
  const keys: Set<string> = new Set();
  localMap.forEach((_v, k) => { keys.add(k); });
  remoteMap.forEach((_v, k) => { keys.add(k); });
```

`keys` 是**两份快照的并集** —— 这是 LWW-Element-Set 语义的骨架：并集决定「有哪些元素」，时间戳决定「每个元素取哪一版」。

### 4.2 三个决策点

```ts
// :31-33 完全相同（三个字段全等）→ 直接留 a，不记冲突
if (a.updateTime === b.updateTime && a.deviceId === b.deviceId && a.isDeleted === b.isDeleted) {
  finals.push(a); return;
}

// :34-41 决胜
let winner = a;
let reason = 'updateTime';
if (a.updateTime === b.updateTime) {
  winner = a.deviceId > b.deviceId ? a : b;
  reason = 'tie_break_deviceId';
} else {
  winner = a.updateTime > b.updateTime ? a : b;
}

// :42-45 败方留档
const loser = winner === a ? b : a;
finals.push(winner);
conflicts.push({ key: k, table, winner: toVersion(winner), loser: toVersion(loser), reason });
```

- **决策一：三字段全等才跳过**。只比 `updateTime` 不够 —— 两台设备可能恰好同毫秒同内容，那是同一个状态而不是冲突。
- **决策二：平局按 `deviceId` 字典序**。注释理由（`设计方案` §6.2）：「确定性决胜，写进文档体现严谨性」。若用随机，同一份数据两次同步结果不同，**无法测试也无法解释**。
- **决策三：败方完整快照进 `ConflictVersion`**（`toVersion` 复制四个字段），不是只记一个「输了」的标记 —— 这是「败方版本可回看」的实现基础。

### 4.3 冲突日志的容量控制

```ts
// :60-62
for (const x of entries) { log.push(x); }
if (log.length > cap) { log = log.slice(log.length - cap); }
```

`slice` 取**尾部**（最新的 cap 条），旧记录丢弃。调用处传 `cap=50`（`SyncScheduler.ets:44`）。

### 4.4 为什么平局决胜曾经是假的

这是全项目最值得学的一个 bug（`设计方案` §6.2 有记录）：

`note_tag` / `favorite_tag` / `tag` 三张关联表原本**没有 `deviceId` 列**。快照里 `deviceId` 恒为空串，平局时 `'' > ''` 为 `false`，于是**远端恒赢**，而日志仍然写着 `tie_break_deviceId` —— **规则名不副实**。

修法见 §5.2：`ALTER TABLE ... ADD COLUMN deviceId ... DEFAULT ''` 原位补列。

> 教训：**「代码路径存在」不等于「规则生效」**。要证明规则生效，必须有一条能失败的断言 —— 这正是 `merge_engine.test.mjs` 10 条用例里那条平局用例存在的意义。

## 5. 持久化：`LocalRdbImpl` 里最硬的四段

791 行，非 UI 文件里最长。这里只讲四个真正的技术点。

### 5.1 逻辑时钟：`nextWriteTime` 的并发串行化

```ts
// :502-515
async nextWriteTime(): Promise<number> {
  const run = async (): Promise<number> => {
    await this.loadLastWrite();
    const t = monotonicNow(this.lastWrite, Date.now());
    this.lastWrite = t;
    await this.setMeta('lastWrite', String(t));
    return t;
  };
  const prev = this.writeChain;
  const next: Promise<number> = prev === null ? run() : prev.then(run);
  // 队列本身不能因为某一次失败就断掉：吞掉结果，只保留时序
  this.writeChain = next.catch((_e: Object): number => this.lastWrite);
  return next;
}
```

注释（:498-501）把为什么必须排队说透了：

> 「读高水位 → 算新值 → 回写，三步之间都有 `await`。两个并发写若交错，后一个会读到前一个尚未回写的旧高水位，各自算出同一个时间戳 —— **这正是本类要消灭的并列**。这里把调用排成一队：前一个彻底落库后，后一个才开始读数。」

**这是容易漏的并发正确性**：单看 `monotonicNow`（纯函数，3 行）会觉得没问题，但它是被异步包裹的，**没有这道 promise 链，纯函数保证不了任何事**。

配套的是高位吸收：

```ts
// :491-496
// 外来到的版本号也要抬高本地高水位：本机时钟若慢于对端，合并进来的记录
// updateTime 会明显大于本机 lastWrite，此时再写 6/7 会立刻输给那条记录。
private observeSyncedTime(updateTime: number): void {
  if (updateTime > this.lastWrite) { this.lastWrite = updateTime; }
}
```

`observeExternalTime`（:521-527）是同一语义的公开入口，给**档案导入**用 —— 导入的版本号来自导出设备，可能大于本机高水位，不吸收的话「导入完本机下一笔写入立刻输」。

### 5.2 复合主键 → 单列 `row_id` 的就地迁移

起因是官方限制：**不支持将含复合键的表设为分布式表**（详见 §8）。

```ts
// :213-232
// SQLite 无法直接改主键，只能「建新表 → 搬数据 → 删旧表 → 改名」。
// 幂等：row_id 已存在说明迁过了，直接跳过。
const specs = [
  { name: 'note_tag', pk: ['note_id', 'tag_id'] },
  { name: 'favorite_tag', pk: ['target_key', 'tag_id'] },
  { name: 'progress', pk: ['target_key', 'section'] }
];
for (const spec of specs) {
  const cols = await tableColumns(st, spec.name);
  if (cols.length === 0) { continue; }          // 表还不存在，交给 DDL 建
  let migrated = false;
  for (const c of cols) { if (c.name === 'row_id') { migrated = true; break; } }
  if (migrated) { continue; }                    // 已迁过
  const expr = `${spec.pk[0]} || char(31) || ${spec.pk[1]}`;
```

三个细节：

- **`|| char(31) ||` 在 SQL 里拼 `␟`**，与 TS 侧 `pairRowId()`（:84-86 用 `\u001f`）**必须一致**，否则逻辑身份对不上、同步行不收敛。
- **迁移失败不阻断启动**（:248-254）：`blocked.add(spec.name)` 后继续，旧表原样保留，「功能照常，只是该表不能设分布式表」。这是**降级而非崩溃**的取舍。
- **`ALTER TABLE ADD COLUMN` 补两根列**（:256-259）：`deviceId` 与 `isDeleted`，`DEFAULT ''`。SQLite 原生支持，不需要重建表。

### 5.3 `applyMerged` 为什么不删本地行

```ts
// :417-424
// 只 upsert 合并终态，不删「合并结果里没有」的本地行。
//
// 合并是 local ∪ remote：快照时已经存在的每个 key 必然出现在终态里；
// 终态里没有的 key，只可能是快照拍完之后、落库之前新写入的行。
// 原先的删除循环恰好会把这些"同步期间的新写入"静默删掉——谓词复用只是
// 把问题从"删第一条"放大成"删多条"。删除语义已经由墓碑和 done=0 表达，
// 不需要物理删行。
```

**这是一段典型的「看似多余其实是必需」**：初版写了「不在终态里就删掉」，看起来是清理，实际会**吃掉同步窗口内的新写入**。因为墓碑已经表达了删除，物理删除没有语义价值，只有风险。

### 5.4 列名白名单防注入

```ts
// :106
const SAFE_COLUMN: RegExp = /^[a-z_][a-z0-9_]*$/i;

// :437-444
for (const c of cols) {
  if (!SAFE_COLUMN.test(c)) { continue; } // I-2：远端 payload 键须过列名白名单，杜绝列名注入
  if (m.keyCols.includes(c) || c === m.updateTimeCol || c === m.deviceCol || c === m.deleteCol) {
    continue;
  }
  allCols.push(c);
  bucket[c] = r.payload[c];
}
```

**为什么这里真有注入面**：`r.payload` 来自对端设备（或导入的 JSON），列名会被拼进 `INSERT ... (col1,col2,...)`。值走 `?` 占位符没问题，**列名不能参数化**，所以必须白名单。

注释还标了「I-2」—— 说明这个修复有编号、有出处，不是随手加的。

### 5.5 一个 SDK 坑：`pragma_table_info` 不能用绑定参数

```ts
// :108-113
// ⚠️ 表名必须内联进 SQL，不能用占位符：实测 `pragma_table_info(?)` 传绑定参数
// 返回**零行且不报错**，迁移会被静默跳过（2026-10-11 真机验证）。
async function tableColumns(st: relationalStore.RdbStore, table: string): Promise<ColumnSpec[]> {
  const rs = await st.querySql(`SELECT name, type FROM pragma_table_info('${table}')`);
```

**「零行且不报错」是最坏的一类失败** —— 迁移被静默跳过，表结构没变，直到同步时才暴露。所以注释强调「表名只来自本文件的 DDL 常量，不含外部输入，内联无注入面」，把安全理由也写清了。

## 6. 纯函数层：为什么「禁 @kit」是一条硬规矩

### 6.1 转译链路

`tools/merge-tests/run.mjs` 把 `.ets` 当 TypeScript 剥成 `.ts` 放进 `tools/.tsbuild/`，再由 `node --test` 执行。`run_gates.py` 的第 12 道门禁 `tsbuild` 就干这个。

能转译的前提：**文件里不能出现任何 `@kit.*` import**（Node 解析不了鸿蒙的系统模块）。于是「禁 @kit」不是风格偏好，是**测试能力的前置条件**。

目前转译的 21 个文件（对应 21 套测试）：`common/` 下 5 个（DesignTokens / EraTheme / Labels / Time / ZoomMath）+ `model/` 3 个 + `repository/` 3 个（IDataRepository / ITransport / LoopbackAdapter）+ `service/` 19 个。

> 注意 `repository/LoopbackAdapter.ets` **也能进转译** —— 它实现传输但刻意不 import `@kit`，所以仿真的交接语义可以在 Node 里断言。这是「把可测的边界往外推」的例子。

### 6.2 内容解析：一份坏 JSON 不能拖垮 41 份好内容

```ts
// ContentParse.ets:113-124
export function parseAllReport(raws: string[], names: string[]): ParseReport {
  const out = new ParseReport();
  for (let i = 0; i < raws.length; i++) {
    try {
      out.sites.push(parseSiteJson(raws[i]));
    } catch (e) {
      const name = i < names.length ? names[i] : `${i + 1}`;
      out.failed.push(name);
    }
  }
  return out;
}
```

配套的返回值设计（`ContentRepo.ets:8-14`）：

> 「页面要区分「全空」和「坏了 1 份」，只返回 `SiteInfo[]` 是分不出来的。」

所以 `ContentRepo.loadReport()` 返回 `{ sites, failed, total }` 三件套。页面据此能显示「全部 42 份都无法解析」vs「39 份成功、3 份失败」——**两种情况的 UX 完全不同**。

### 6.3 枚举校验在解析层，不在 UI 层

```ts
// ContentParse.ets:70-72
if (!ERAS.includes(s.era) || !CITIES.includes(s.city) || !SITE_TYPES.includes(s.siteType)) {
  throw new Error(`${s.id}: 枚举值非法`);
```

三维度枚举在这里就被拦死。好处是**UI 永远不用防御非法年代值**，`eraColor(era)` 之类的函数可以直接查表。

### 6.4 推荐：零分候选不进结果


以及配额兜底：

```ts
// :93-96
// 先在分数序上按配额收，收不满 topN 再按分数序放宽补足——
// 语料只有 42 条，硬配额会把"洛阳 12 条"削成 5 条后补进一堆零相关项。
// 补的时候仍沿原分数序走，避免列表出现"低分排在高分前面"。
```

**这是「算法规则」与「语料规模」耦合的自觉**：配额在别的数据集上可能合理，在 42 条语料上会削出空洞，所以要兜底。

### 6.5 导入：保留原时间戳，不重新盖章

```ts
// ImportPlan.ets:7-15
// 导入的每条记录保留导出时的 updateTime 作为同步版本号，**不用本机当前时间
// 重新盖章**。这样：
//   - 本机在导出之后又编辑/删除过同一条 → 本机版本号更新 → LWW 保本机；
//   - 两台设备各导入同一份档案 → 版本号相同、内容相同 → 无论谁赢都收敛；
//   - 本机时钟若慢于导出设备，后续写入会因高水位吸收（observeExternalTime）
//     仍大于导入版本，不会被导入内容整批压住。
```

**三条都是「不这么做会怎样」的推理**，而不是「这么做更好」。这是这个仓里注释的普遍风格：先写失败场景，再写做法。

## 7. 页面层：三个可复用的模式

（21 个页面的逐页职责见 §10 速查表。）

### 7.1 冷启动闸门：让首屏不等数据库

`service/sync/BootGate.ets`（38 行）。问题背景（:3-15）：

> 原实现里 `EntryAbility` 等 `AutoSync.prepare()` 完成（要打开 RDB、老库还要跑迁移、再按 `syncMode` 切档案）才 `loadContent`，于是首页骨架、语料这些**完全不依赖数据库的东西也被一起按住**。
> 但「先恢复模式」这个顺序本身是有理由的 —— 首页若先读主库，等模式切到仿真档案后又不重读，用户会看到「数据少了一半」。

解法是把这个顺序约束**下沉成一道闸门**：

```ts
// :21-31
const gate: Promise<void> = new Promise<void>((resolve): void => { openGate = resolve; });

export function releaseBootGate(): void {
  if (released) { return; }          // 多次调用安全：只有第一次生效
  released = true;
  ...
}

// :36-42 带超时兜底
export async function whenBootGate(): Promise<void> {
  if (released) { return; }
  const fallback = new Promise<void>((resolve): void => {
    setTimeout((): void => { resolve(); }, GATE_TIMEOUT_MS);   // 3000ms
  });
  await Promise.race([gate, fallback]);
}
```

`Promise.race([gate, fallback])` 这一行是精髓：**即使 `prepare()` 从未被调用（比如异常路径），页面也不会被吊死**，3 秒后按默认口径继续。

`UserDataRepo.get()` 把它放在最前面（:30）：

```ts
static async get(context): Promise<IDataRepository> {
  await whenBootGate();     // 模式没就绪就不给库
  if (UserDataRepo.simActive) { return await UserDataRepo.simRepoOf(context, UserDataRepo.currentSim); }
  ...
}
```

**因为所有页面读写都走 `get()`，所以闸门只需要放一处。**

### 7.2 重复初始化：共享 Promise

```ts
// UserDataRepo.ets:14-18
// init 进行中的共享 Promise：首页与「我的」页会并发调 get()，
// 而 impl 只在 init 完成后才赋值。两边都往下走会各自 new 一个 LocalRdbImpl，
// 两个实例同时对同一批表跑迁移/建表 —— 实测表现为 hilog 里 db ready 打两遍，
// 且其中一个实例的 DROP TABLE 把另一个刚搬完的数据删掉（2026-10-11 真机踩到）。
private static pending: Promise<IDataRepository> | null = null;
```

**这个 bug 的严重性值得记住**：并发初始化不只会「多创建一次」，还会让 A 实例的 `DROP TABLE`（迁移的一步）**删掉 B 实例刚搬完的数据**。所以「用 pending Promise 去重」是数据安全要求，不是性能优化。

### 7.3 状态同步：普通类只能靠 AppStorage 镜像

`SyncStatus.ets` 是普通类（非 `@Component`），改字段不会触发 UI 刷新。但底栏的冲突角标必须跟着变：

```ts
// :19-27
// SyncStatus 是普通类，刷不了 @Component；底栏要跟着冲突数变，
// 只能把「冲突数」这一件事镜像到 AppStorage，由 AppNavBar 用
// @StorageProp 订阅。快照本身仍是唯一事实源，这里只做单向镜像。
export const SYNC_BADGE_KEY: string = 'syncConflictBadge';

function publishBadge(): void {
  AppStorage.setOrCreate(SYNC_BADGE_KEY, current.conflictCount);
}
```

**「唯一事实源 + 单向镜像」**：`SyncSnapshot` 仍是唯一真值，`AppStorage` 只镜像一个数字。这避免了「两个地方都存状态、互相打架」。

### 7.4 错误分类：别把三种失败都写成「同步失败」

```ts
// SyncStatus.ets:38-52
// 把底层异常翻译成用户能理解的三类。SDK 的报错文案不稳定，
// 只能按关键字归类；归不进去的一律算传输失败，至少不会误报"已授权"。
export function classifySyncError(msg: string): string {
  const m = msg.toLowerCase();
  if (m.includes('permission') || m.includes('unauthorized') || m.includes('201') || ...) {
    return 'auth';
  }
  if (m.includes('peer') || m.includes('no device') || ... || m.includes('组网')) {
    return 'no_peer';
  }
  return 'failed';
}
```

**「SDK 报错文案不稳定，只能按关键字归类」** 是一句老实话：这是在契约不可靠时的务实处理。而「归不进去的一律算 `failed`」是**保守失败方向** —— 宁可说「失败」，不能误报「已授权」。

### 7.5 页面层的三个语法坑（实测代价）

**坑一：「可见性桥」——`onPageShow` 只在 `@Entry` 上触发**

`FavoritesPage` 与 `NoteCenterPage` 都是「`@Entry` 壳 + `export struct XxxBody`」结构。body 是子组件，**写在它里面的 `onPageShow` 永远不会响**。

`NoteCenterPage.ets:142-144` 记着这个代价：
> 「`onPageShow` 只在 `@Entry` 上触发，本 body 是 `@Entry` 壳的子组件，写在这里永远不会响 —— 从编辑器/关联页返回时列表停在旧数据上（实测：写了 4 条笔记，回来仍显示『共 0 条』）。」

解法是把可见性变成自增数，交给 body 的 `@Watch`：
```ts
// FavoritesPage.ets:859-860
// 页面可见性桥：onPageShow 只在 @Entry 上触发，把它记成一个自增数，
// 交给 body 的 @Watch——否则在详情页收了藏再返回，展厅还是旧的。
@Prop @Watch('onPageTick') pageTick: number;
```
这两个文件也是**全项目仅有的 2 处 `@Watch`**。

**坑二：`@Builder` 的参数按值拷贝，不会响应状态**

`ArchivePage.ets:102-103` 记着实测：
> 「`@Builder` 按值传参，计数只会停在首帧 —— hilog 实测 promise 已带回 favs 9，卡上还是『0 条』。」

所以三处都改成了**独立 `@Component`**：

- `ArchivePage` → `ArchiveEntryCard`（:249）
- `ExportPage` → `CountCell`（:75），注释「计数必须走独立 @Component：@Builder 的参数按值拷贝，异步读回来的…」
- `设计方案` T15 → `StatCell`

**坑三：`@Builder` 里必须直读 `this.xxx`，不能当参数传入**
（`docs/OPEN_SOURCE_REFERENCES.md:297-298`：「发现页筛选 chips 曾因此高亮失灵」）

> 三条合起来是一句话：**`@Builder` 只负责「结构复用」，不负责「状态响应」**。要响应状态，就用子组件 + `@Prop`；要跨 `@Entry` 边界刷新，就用自增数 + `@Watch`。

### 7.6 三个「刻意不通用」的取舍

看页面代码时会发现一些「不够优雅」的地方，它们都有理由：

- **`ListPage.ets:30-31`**：材质条读的字段必须是 `@State` —— 「非响应式字段只会在首帧渲染一次，之后改城市/类型筛选，列表数字变了而『当前 N 件』还挂着旧值」。
- **`SearchPage.ets:7-8`**：「不做模糊纠错、不做拼音、不做全文分词。语料只有 42+104+笔记，子串匹配足够，也不会把『没匹配』伪装成『相关』。」
- **`RecommendPage.ets:45`**：「单条与整类的区别只在『排掉一行』还是『排掉一组』，不做权重衰减 —— 本地语料只有 42 条，半衰期参数没有数据支撑，不如行为直接可预期。」

**共同逻辑**：语料规模（42 条）被当成设计参数，而不是被忽略。这是这个小数据集项目最容易做错的地方——套用大数据集的做法会引入无数据支撑的复杂度。

### 7.7 深色页的对比度红线

`RelicPage.ets:9-10` 记着一条硬约束：
> 「交互色走 `ON_DARK_GOLD`（7.82:1 @ PANEL），**不得退回 ACCENT** —— #9C4A2F 在 #1C1A18 上只有 2.84:1。」

文物页是全 App 唯一深色页（「展柜看文物的『暗』有动机」）。同一条色在不同底上对比度差 2.7 倍，所以**颜色令牌必须跟底色配对使用**，不能全局换。

同文件 :13-14 还有一句价值观声明：
> 「剪影占位的『待入藏』是诚实的占位，别改成好看的空壳。」

### 7.8 「最近删除」为什么没有彻底删除

`RecyclePage.ets:3-9` 开头就是一段完整的因果论证：

> **为什么只做「恢复」不做「彻底删除」：**
> 本项目的删除是软删（`isDeleted=1` + 新 `updateTime`/`deviceId`），墓碑行还要参与 LWW 合并 —— **物理删除会让对端把「删除」读成「从未存在」，下一次同步又把旧行推回来**。回收站因此只读墓碑、只翻回 0，不碰 `DELETE`。
> **30 天窗口在查询里**（`updateTime >= since`），页面不自己过滤：两处各写一个阈值，迟早会出现「列表里没有、却还能恢复」的幽灵条目。

**两段话对应两个不同层面的正确性**：
1. **分布式语义**：物理删 = 让合并引擎失去「这里曾经有过一条」的信息，对端的并集会把它带回来。**这是 LWW-Element-Set 必须用墓碑的根本原因**（`MergeEngine` 的规则 2 也依赖它：「一方是墓碑而对方存活时，仍按时间戳裁决 —— 删除本身就是一次编辑」）。
2. **单一真值**：阈值写在查询里而不是页面里，避免屏幕上和数据库里对「30 天」有不同理解。

> 这类注释的价值在于：**它记录的是「为什么不能那样做」，而不是「代码做了什么」**。读实现看不出物理删除有什么错，读注释才知道那个错会以「数据复活」的形式在几天后出现。

## 8. 官方约束如何改写了代码

这几条来自官方《关系型数据库数据同步》页的「约束限制」章节 —— **SDK 的 `.d.ts` 里查不到**。

| 官方限制 | 代码里的落点 |
|---|---|
| 不支持将**含复合键**的表设为分布式表（判据是复合主键，不是"有没有主键"） | 三张关联表改单列 `row_id`（`LocalRdbImpl.ets:24-33` DDL + `:213-255` 迁移） |
| 只支持**最终一致**，不支持强/弱一致 | 全仓措辞不写「实时一致」；`README` 已知限制、`SoftBusRdbTransport.ets:64-66` 主动写「三步不是事务」 |
| 单应用最多 16 个分布式 RDB 库、单库最多 8 个变化订阅回调 | 本项目 1 个库、1 个 `dataChange` 订阅 |
| 端端与端云**不可混配**、同库必须同存储机制 | 全用 `relationalStore`，无 KVStore 混用 |
| 单版本表模式（API 23+）需 `rawfile/arkdata/schema/sync_schema.json` + UUID 解冲突列 | **未采用**，走无 type 重载的默认设备间同步（表是 `TEXT PRIMARY KEY`，无 UUID 列） |

**`DISTRIBUTED_TABLES` 直接指向 `SYNC_TABLES`**（`SyncModels.ets:54`），注释说明：「本 SDK 不支持设置 schema，默认不读取 schema 文件 —— 所以这里用的是默认模式，无需落地 `sync_schema.json`」。这说明作者**核过 SDK**，不是照抄文档。

## 9. 门禁与转译：13 道怎么串起来

`tools/run_gates.py` 的 `GATES` 列表顺序**即依赖顺序**（注释 :66-67）：

> 「内容校验在样式门禁之前，因为 JSON 结构错时后面的视觉门禁只会跟着误报。」

13 道依次是：
`validate`（schema+图片引用+反向差集）→ `validate-src`（母本一致）→ `attribution`（署名三向对账）→ `poems`（42 址每站 ≥1 首）→ `contrast`（58 项）→ `tokens`（裸值）→ `visual`（跨页间距）→ `aging`（字号档位）→ `a11y`（读屏标签+动效令牌）→ `motion`（按压/转场）→ `font`（字族字重）→ `tsbuild`（`.ets`→`.ts`）→ `unittest`（Node）。

**其中 `validate` 有两条容易忽略的设计**：

1. **反向差集**：不仅查「引用的图片存在吗」，还查「盘上的图有没有人引用」—— 没人引用的图也会被打进 HAP，白占 40 MB 额度。
2. **母本与发布版分离**：`tools/sites-src` 是母本（留全量语料），`rawfile/sites` 是发布版。`validate-src` 校两者 schema 一致，注释记录「往返断言拦下过一次会炸开排版的改写，母本最终零改动」。

## 11. 读代码时的六个提醒

1. **`service/` 下看图不看目录**：`sync/` 两个文件有副作用，其余 19 个是纯的。判据是文件头有没有写「禁 @kit」。
2. **`\u001f`（␟）是全项目的逻辑身份分隔符**，TS 侧 `pairRowId` 与 SQL 侧 `char(31)` 必须一致。
3. **看到 `nextWriteTime()` 就知道这条写会进同步域**；直接 `Date.now()` 的地方（如 `visit` / `reco_feedback`）就是刻意不同步的。
4. **`applyMerged` 只 upsert 不删** —— 看到「为什么没删」时别以为是漏了，§5.3 有理由。
5. **`@Builder` 不响应状态**，要响应就拆子组件 + `@Prop`。
6. **注释常写「曾经错在哪」**（时钟并列、双袋覆写、删同步期新写、pragma 绑定参数）。这些是这个仓最有价值的部分，**比读实现更能理解边界**。
