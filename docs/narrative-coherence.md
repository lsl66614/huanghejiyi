## 一、先说结论

**骨架是好的，缝合是乱的。**

三层数据结构（语料只读 / 个人数据读写 / 元层）设计成立，`target_key` 作为全站通用
货币把 19 屏缝成一体，这套抽象是本项目最有说服力的部分。

但**导航层与内容层的叙述已经脱节**，具体表现为三类突兀：

| 级别 | 现象 | 影响面 |
|---|---|---|
| **结构性断裂** | 首页「遗址⇄文物」分段根本不存在；`RelicListBody` 抽出来了没人用 | 赛题 F1 双实体条款无 UI 落点 |
| **语法不统一** | 四个频道页有四种不同的头部写法；正文里混着三级 tab 组件 | 观众感到"不是一个 App" |
| **语义倒置** | ~~`SyncPage` 标签在标题之上~~ ✅已修；`NoteCenterPage` 底栏高亮打在"同步"格 | 演示时读作"没做完" |

## 二、页面内在联系：抽象是成立的

### 2.1 三层数据结构（实测成立）

```
语料层（只读）   rawfile/sites/*.json  42 遗址 + 104 文物
                 └→ ContentRepo（缓存单例）→ 多数屏
个人数据层（读写）RDB 六表（进同步域）+ visit（本地）
                 └→ UserDataRepo → 多数屏
元层             SyncStatus（全局快照）· AttributionRepo（101 条）· RouteRepo（7 条）
```

### 2.2 缝合货币：`target_key`

全站个人数据都挂在同一个键空间上：

| 键形 | 含义 | 挂载点 |
|---|---|---|
| `site:{id}` | 遗址级 | 收藏 / 笔记 / 进度 / visit |
| `relic:{id}` | 单件文物 | 同上 |
| 五段 section | 遗址某一段（考古/历史/诗词/文旅/参观） | 进度挂 `(target_key, section)` |
| `notebook:inbox` | 随手笔记 | 仅笔记 |

因为键空间统一，**任意两屏共享挂载点**——这是"19 屏是同一份数据的 19 种投影"
这句话的技术依据，不是修辞。

### 2.3 五种边类型（实测成立）

| 类型 | 例子 | 实现证据 |
|---|---|---|
| **下钻** | 地表→地层→遗址→展柜 | `Index→ListPage→DetailPage→RelicPage` 四级 `pushUrl` |
| **回流** | 展柜→所属遗址 | `RelicPage` 所属遗址卡 → `DetailPage` |
| **派生** | 收藏+标签→网络图；visit→推荐；progress→路线完成度 | `NetworkPage`/`RecommendPage`/`RoutePage` |
| **同步** | 六表→MergeEngine→冲突台账；SyncStatus→状态条+角标 | `SyncStatus` 镜像到 `AppStorage[SYNC_BADGE_KEY]` |
| **元数据** | Attribution→版权页+灯箱逐张署名 | `CreditsPage` + `ImageViewer.credits` |

### 2.4 三条隐形主线

1. **年代主线**：`eraColor` / L1–L6 在卡脊、章、chips 色点、导览尺、网络图节点、
   推荐理由里以不同形态出现，**从不裸色**（块面/浅底/深底三套令牌）。
2. **双实体主线**：site/relic 同构贯穿收藏、笔记、进度、推荐、网络图、搜索、导出。
3. **诚实主线**：`real_` 才上屏；缺图走材质线稿标"待入藏"；每张实拍双重署名；
   AI 图仅限首页 6 张年代封面。

**这三条主线是本项目叙述质量的地基，全部成立。**

## 三、突兀点逐条（按严重度）

### ✅ P0-1 双实体首屏落点 —— 已用 A 方案解决（2026-11-04）

**原问题**：`Index.ets` 中 `SegmentTab` 出现 0 次，`RelicListBody`（`RelicListPage.ets:45`）
全站只被自己文件里的兼容壳调用（`:624`），**首页零引用**。
而 `Index.ets:414-418` 的注释写着「现在顺序固定：页头 → 同步条 → 分段 → 分支内容」——
**这是一段"修完了但代码没跟上"的注释**。

**为什么不做首页并列分段**（用户判断 + 代码核实，两条都成立）：

1. **布局冲突**：`Index` 的 `Scroll` 已 `layoutWeight(1)`，而 `RelicListBody` 的
   `Grid` 也用 `layoutWeight(1)`——嵌套权重分配不可控。
   （注：`RelicListBody` **无竖向 `Scroll`**，三个 `Scroll()` 全是横向筛选行，
   故不构成竖向嵌套冲突；真正的冲突是权重与"单列内容流中插一块网格"的节奏。）
2. **推翻既有决策**：`Index.ets:74-78` 明确写过——
   > 「首页不再有文物图录 / 主题路线入口——两者是「我的」的第 03、04 行，
   > 在首页重复出现会让第一屏读作仪表盘而不是档案本身。」

**A 方案（已落地）**：双实体不做首页并列分段，做进**年代轴**——
每张年代卡上并列给出「N 处遗址 · M 件文物」两个数字，两个数字各自可点落到对应实体。

| 落点 | 实现 | 装机实证 |
|---|---|---|
| 年代卡双轴计数 | `common/StrataSpineCard.ets` 新增 `relicCount`；`pages/Index.ets` 经 `buildEraRelicStats` 传入 | 仰韶卡显示「10 处遗址 · 21 件文物」 |
| 年代卡 → 该层文物 | 年代卡点击 → `ListPage`（带 era）→ 顶栏「仰韶层文物 ›」→ `RelicListPage`（带 era） | 图录页「当前 21 件 / 共 104 件 · 全部有实拍」 |
| 遗址条目挂文物数 | `pages/ListPage.ets` 每条遗址下加「N 件文物」 | 渑池 2 件 / 庙底沟 3 件 / 濮阳 2 件 |

**关键口径（易错，已被单测钉死）**：文物的年代取 `RelicInfo.era`（器物自己的年代），
**不是**所属遗址的年代。语料 104 件里 **12 件跨代**（宋代巩义窑址出土汉唐唐三彩、
龙山遗址出仰韶陶片等）。按遗址年代计，这 12 件会落错层、全站总数会重复计。
纯函数 `service/content/EraRelicCount.ets` + 9 条 Node 单测锁死：
六层遗址数之和 = 42，六层文物数之和 = 104。

截图：`design/verify/nav/plan_a_03_eracard.jpeg`（年代卡双轴）、
`plan_a_06_relic_era.jpeg`（年代筛选后的图录）。

### 🟠 P1-1 `SyncPage` 标签在标题之上 ✅ **已修 2026-11-04**

**原证据**：`SyncPage.ets:406-428` 的顺序是

```
Scroll(Horizontal) → SegmentTab（仿真/真机模式）
  ↓
SectionTitle({ title: '同步面板' })
```

即**传输模式 tab 浮在页面标题上方**，而标题反而在 tab 下面。观众第一眼看到的是
两个可点的小标签，然后才知道这页叫"同步面板"。

这正是 `docs/修复计划.md` §7.8 记的 V1 病（"分段 tab 浮在印章+标题之上"），
在 `Index` 上修好了，**在 `SyncPage` 上是同一个病没修**。

**修法**：把刊头 `SectionTitle` 提到模式 `SegmentTab` 之前，刊头 `top` 由 10 提到 16
（成为页首元素，需要与状态栏拉开距离）。

**装机实证**（模拟器 127.0.0.1:5555，UI 树 + 截图 `design/verify/nav/sync_04_after.jpeg`）：

| 元素 | 修后 bounds | 关系 |
|---|---|---|
| 同步面板（标题） | `[60,165][429,285]` | 上 |
| 仿真同步 / 真机分布式（标签） | `[407,351][630,447]` / `[654,351][913,447]` | 下 |

门禁 13/13、构建 `BUILD SUCCESSFUL`、屏上顺序为「先标题后控件」。

### 🟠 P1-2 `NoteCenterPage` 底栏高亮打在"同步"格

**证据**：`NoteCenterPage.ets:618` → `AppNavBar({ active: 2 })`。
按 `AppNavBar.ets:27`，`NAV_URLS = ['pages/Index','pages/ArchivePage','pages/SyncPage','pages/MinePage']`，

**缓解**：`NoteCenterPage` 与 `FavoritesPage` 都已从 `main_pages.json` 摘除，
只能作为组件被 `ArchivePage` 内嵌（`showNav=false`），所以这段死代码
**当前屏上不可见**。但它是一颗定时炸弹：谁把 `showNav` 改回 true 就会亮错格。

### 🟠 P1-3 三个 tab 组件并存，正文里没有层级

全站同时存在：

| 组件 | 形态 | 用在 |
|---|---|---|
| `SegmentTab` | 填充式药丸 | 收藏视图切换、笔记 scope、同步模式 |
| `UnderlineTabs` | 下划线 | 档案页四分段（收藏/笔记/研读/网络图） |
| `SegmentTab`（另） | 横向滚动 | — |

**问题**：`ArchivePage` 的"收藏/笔记/研读/网络图"是**一级分段**，用了
`UnderlineTabs`；但它内嵌的 `FavoritesBody` 里又嵌了一层 `SegmentTab`
（按标签/按时间），`NoteCenterBody` 里嵌了两层 `SegmentTab`（scope + tag）。
观众在档案页点一下 tab 后，页内还有 1–2 层 tab，**没有视觉降级**。

`UnderlineTabs` 全站只被 `ArchivePage` 一处使用——它是为档案页量身定制的，
不是通用件。

### 🟡 P2-1 `StratumCrumb` 层级面包屑只覆盖 2 个页

**证据**：`StratumCrumb` 只在 `ListPage.ets:153` 和 `RelicListPage.ets:370`

## 四、"叙事突兀"的根因

**三层问题其实是一件事：架构层（数据缝合）做得比叙述层（信息架构）扎实得多。**

- 数据层有三层结构 + 通用键 + 五种边 + 三条主线，**可验证、可演示**。
- 叙述层靠**逐页手写头部 + 逐页手写分段**，没有共用件，于是：
  - 频道页头部四写法 → 切格时视觉跳变
  - 分段组件三形态 → 层级感缺失
  - 面包屑只覆盖两屏 → 深层坐标丢失
  - 首页分段缺失 → 双实体条款无落点
  - 状态条三处形态不一 → 同一语义三种外观

**一句话**：**内容缝合得再好，观众每翻一页还是要重新学一遍这页的语法。**
